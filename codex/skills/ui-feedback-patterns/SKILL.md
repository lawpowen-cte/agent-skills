# UI 提示、浮层与引导选型

把“加个弹窗”转成具体的组件、交互和验收条件。优先减少无必要的打断，同时保留用户输入和必要的操作确认。沿用项目现有组件库、设计系统和用户指定的方案。

## 先判断任务，再选组件

先查看现有页面、触发操作和相关组件，确认信息是否重要、是否要求立即行动、操作能否撤销，以及是否需要保留原页面上下文。非关键歧义采用明确的假设；只有会改变业务行为或数据后果的缺失信息才需要澄清。

| 组件 | 适合的任务 | 关键边界 |
|---|---|---|
| Tooltip 文字提示 | 字段、图标的补充解释 | 不藏必读信息，不放需要点击的按钮或表单；支持键盘焦点触发 |
| Toast / Message 轻提示 | 保存成功、复制成功等简短结果反馈 | 不抢焦点；失败原因、补救入口和关键操作结果不能只存在于短暂提示中 |
| Alert 页内提示 | 与当前页面或区块有关、需要持续可见的状态或警告 | 通常不阻断任务；不能仅靠黄色或红色传达含义 |
| Modal 模态对话框 | 简短且需要聚焦处理的输入、决定，或不可逆操作的确认 | 真正模态时，底层不可交互；不要用于每次成功反馈 |
| Popconfirm 气泡确认 | 靠近触发按钮的简单确认，例如列表中的单项操作 | 内容和选择应简短；复杂解释、重要后果或多个字段需要更合适的容器 |
| Drawer 抽屉 / 侧面板 | 保留列表上下文的详情、编辑或连续处理记录 | 侧滑外观不等于非模态；按实际行为决定底层能否交互 |
| Bottom Sheet 底部面板 | 窄屏中的上下文内容、详情或短任务 | 区分模态与非模态；高度与吸附档位由内容和视口决定，不能默认固定为半屏 |
| Action Sheet 动作选单 | 用户主动发起操作后，选择少量相关动作 | 使用目标平台组件；外观可能是底部面板或锚定浮层，不硬编码“底部按钮组” |
| Snackbar 可带操作的轻反馈 | 操作结果及可选的“撤销”等简单动作 | 动作不是必填；真实实现撤销，关键补救入口不能只依赖短暂提示 |
| AlertDialog 警报对话框 | 需要立即回应的简短重要消息或高后果确认 | 属于模态对话框；提供安全取消路径，不能因为“高危”就统一禁用 Esc |
| Tour 分步引导 | 必须结合具体控件说明的产品流程 | 可跳过、可退出；目标不存在时不能卡住，必需说明仍在正常界面可获得 |
| Lightbox 媒体查看器 | 放大查看图片等媒体 | 遮罩与缩放不是充分定义；按模态行为管理焦点，操作有按钮和键盘入口 |
| Inline error 字段错误 | 与单个字段直接相关的校验失败 | 明确原因与修正方式，关联字段；纠正并通过相应校验后更新，不按秒消失 |
| 独立页面 | 独立流程、多个步骤或需要独立导航与恢复的任务 | 例如从购物车进入结算；不要把完整流程硬塞进小浮层 |

Tooltip、Toast 等是设计模式名，未必是组件库中的实际 API 名称。实现前核对项目安装版本和现有封装，不为匹配术语而新增组件库。

涉及上述新增组件时，按需读取 [组件边界与核实记录](references/component-selection.md)。其中区分官方定义、平台行为和本技能的工程建议；API 名称相同也不保证默认行为相同。

### 容易混淆的边界

Bottom Sheet 主要描述承载内容的面板，Action Sheet 主要描述选择动作的任务；二者不能仅凭“从下面出现”互相替代。Toast 与 Snackbar 在不同组件库中可能重名或重叠，按是否需要操作、是否持久以及实际读屏行为选型。AlertDialog 的 `alertdialog` 是有特定用途的 ARIA 语义，不是红色外观的别名。[依据：Apple Action sheets](https://developer.apple.com/design/human-interface-guidelines/action-sheets)、[Android Bottom sheets](https://developer.android.com/develop/ui/compose/components/bottom-sheets)、[Android Snackbar](https://developer.android.com/develop/ui/compose/components/snackbar)、[W3C APG AlertDialog](https://www.w3.org/WAI/ARIA/apg/patterns/alertdialog/)。

Tour、Lightbox 的具体可退出、缩放和替代入口方案是本技能的工程建议；Web 中如采用模态浮层，仍遵循下方模态焦点与关闭约束。视频所称 Inline Alert 若指单字段校验，按 Inline error 处理；一般页内提示仍按 Alert 选型，不把这两个名称视为统一组件 API。字段错误用 `aria-invalid` 标识失败状态，并以 `aria-describedby` 等方式关联具体修正说明；动态消息按需要通告，不能只变红。[依据：W3C 表单通知](https://www.w3.org/WAI/tutorials/forms/notifications/)。

## 弹窗、抽屉与页面的取舍

结合内容长度、上下文和任务流程选择，不能只凭表单字段数量决定。

- 内容少、任务短且需要集中注意力：优先考虑 Modal。
- 需要保留列表、查看记录详情或连续编辑：考虑 Drawer 或页面内侧面板。需要真正同时操作列表时，选择允许底层交互的布局，不假设带遮罩的 Drawer 可以做到。
- 内容较长但仍是原任务的子任务：评估较大的侧面板、分段表单或独立页面，避免过深滚动和多层嵌套。
- 已进入新的业务流程：考虑独立页面，保留合理的返回路径和任务状态。

尺寸使用项目设计 token 和可用视口。视频中的 400/520/720 px 只是示例，不是通用标准；在窄屏和缩放后仍应能读完内容、找到操作按钮。

## 三条防误操作规则

### 保护尚未保存的输入

有未保存修改时，点击遮罩不能直接销毁表单。关闭按钮、取消、Esc 和相关路由离开应遵循一致的输入保护逻辑：保留草稿、自动保存，或明确询问是否放弃。无修改、只读内容可以按项目约定轻量关闭，不把所有浮层一律锁死。

### 按真实可撤销性决定确认

操作影响有限且确实能完整恢复时，优先“执行后提供撤销”，减少反复确认。撤销必须有真实恢复能力和可发现的入口，不能只显示一个没有恢复能力的按钮。

永久删除、对外发送、扣费或其他无法完整恢复的结果需要清楚表达后果并按业务要求确认。回收站、数据库回滚不一定能撤销已发送的信息或其他外部影响。UI 中出现确认框本身不构成执行真实操作的用户授权。

### 按钮写具体动作和后果

使用“取消”“删除项目”“确认扣费并退票”等可独立理解的标签，避免只写“是/否”。对重大操作说明对象、影响和是否可恢复；不可逆操作不要默认把焦点放在危险按钮上。

## 实现时保留的交互约束

- 模态对话框提供可访问的名称；打开时把焦点移入，Tab/Shift+Tab 留在其中，关闭后恢复到触发点或合理的后续位置。只在确实阻止底层交互时声明模态语义。提供可用的关闭或取消路径，Esc 经过同一套未保存保护逻辑。
- Tooltip 不仅靠 hover；触发器可聚焦，提供关联说明并支持 Esc 关闭。触屏上仍需可发现的解释入口，不把必要信息放进只能悬停查看的内容。
- 短暂状态反馈不移动焦点。一般结果反馈使用合适的温和读屏通告；紧急消息才考虑 alert 语义，不因组件叫 Alert 就全部设置为强制打断的读屏通知。
- 不把“约 2 秒自动消失”当作所有 Toast 的定时标准。按内容、项目规范和可访问性决定时长；包含撤销、补救或关键说明时提供足够时间和持续可访问的入口。
- 提交中防止重复操作；成功反馈以实际结果为准，失败时保留已输入内容并给出可操作的修正路径。

依据：[W3C APG Modal Dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)、[W3C APG Alert](https://www.w3.org/WAI/ARIA/apg/patterns/alert/)、[W3C APG Tooltip（该模式仍为工作草案）](https://www.w3.org/WAI/ARIA/apg/patterns/tooltip/)。抽屉上下文用途参考 [Ant Design Drawer](https://ant.design/components/drawer/)，不据此假定其他组件库具有相同 API 或默认行为。

## 交付与验证

按请求交付，不强制把小改动扩展成完整报告。

设计建议说明选用的组件、简短理由，以及必要的关闭、确认和输入保护行为。评审指出具体触发条件、用户影响和修改建议。实现请求应完成相应代码修改，并验证相关行为。

验证覆盖本次变更实际涉及的路径：正常提交、失败后的输入保留、未保存时关闭、重复提交、撤销或不可逆确认、键盘焦点与窄屏可用性。新增模式还应检查：底部面板在软键盘和放大字体下可操作、Snackbar 动作真正可用、Tour 可跳过且目标缺失可恢复、Lightbox 可退出并恢复焦点、字段错误与输入关联且不会提前消失。优先使用已有测试和实际界面检查；仅在有必要保护关键行为时增加测试，不为静态文案或样式机械添加测试。报告已验证项目和仍未验证的限制，不把静态检查称为完整可访问性认证。
