# 聊天与桌面交互

把输入、阅读位置和可调布局当作需要保留的用户状态。先应用 `ui-design-standards` 中的用户规范，沿用项目的发送快捷键、组件、状态管理和平台约定；只处理本次实际涉及的交互，不为局部修复重做整个聊天应用。

## 按问题进入

| 触发问题 | 处理重点 |
|---|---|
| 选中文候选词时发出消息、回车重复发送 | IME 合成状态、快捷键与统一提交入口 |
| 流式回复把历史阅读位置拽走 | 显式跟随状态、用户离开底部、恢复到最新 |
| 桌面分栏拖不稳、跨预览失去拖动、只能鼠标调节 | 拖动状态、取消恢复、最小宽度与可访问分隔器 |
| 文件名截断丢失扩展名或无法辨认文件 | 只裁显示、完整名称可达、保留识别信息 |

相关机制、视频数值的核实结论与官方来源见 [规则核实与参数边界](references/verified-rules.md)。需要确认兼容方案或引入阈值时读取，不把示例数值当默认配置。

## 输入法与发送

Web 发送快捷键先检查合成状态，再判断 Enter、修饰键和项目约定。在合成期间，回车用于候选确认，不触发应用的发送逻辑；不要全局吞掉所有键盘事件或用 `preventDefault()` 阻断正常选字。`KeyboardEvent.isComposing` 是主要信号；`compositionstart` / `compositionend` 可维护本地状态，必要时保留 `keyCode === 229` 兼容判断。该属性已弃用，但 MDN 明确记录了合成边界上仅靠 `isComposing` 可能漏判的情况。[依据：MDN keydown 与 IME](https://developer.mozilla.org/en-US/docs/Web/API/Element/keydown_event)。

按实际目标浏览器与输入法复现边界问题。不要默认加入 compositionend 后 500ms 禁发窗口；如确有兼容缺陷，用有证据的最小补丁，并验证快速正常发送未被误吞。原生桌面或移动端使用目标框架的合成事件能力，不把 Web 的 `229` 搬成跨平台约定。

让快捷键、发送按钮和表单默认提交汇入同一提交逻辑，避免 IME 守卫只保护其中一条路径。按业务处理空内容、连续按键与请求中的重复提交；失败保留草稿并提供重试，发送成功后按正常编辑流程保留或恢复输入焦点。这些是本技能的工程建议，具体并发发送能力由产品决定。

## 消息滚动与流式更新

以下是本技能采用的产品策略，属于工程建议，不能由滚动 API 推导为通用 UX 标准：

- **跟随最新：** 用户原本停在底部或主动选择“跳至最新”时，随新增内容保持在最新位置。
- **阅读历史：** 用户向上离开底部后暂停跟随；后续 token、图片加载和容器变化不应擅自把用户拉回。显示可聚焦的“跳至最新”入口，必要时附新消息数。
- **恢复跟随：** 用户主动返回底部或点击入口时恢复。程序自己滚动触发的 `scroll` 事件，不应被误认成新的用户离开意图。

普通、自上而下列表可用 `scrollHeight - clientHeight - scrollTop` 估算距底部距离，允许小数误差，不能用严格相等；倒序布局、弹性越界和虚拟列表须按实际坐标规则处理。阈值可配置，并避免在边界反复切换；40px/120px 仅是待调参数。[几何机制依据：MDN scrollHeight](https://developer.mozilla.org/en-US/docs/Web/API/Element/scrollHeight)。

追加数据前保留“此前是否跟随”的状态，DOM 更新后再按该状态滚动；不要每次渲染无条件 `scrollIntoView()`。向前加载历史时保留可见消息及其偏移，优先使用现有虚拟列表的锚点能力。流式更新合并布局工作，避免每个 token 都新建平滑滚动。这些是实现策略，须在目标列表验证。

新消息不抢键盘焦点。顺序追加的聊天记录可评估带名称的 `role="log"`，其默认通告为 polite；流式内容按消息或合适批次通告，避免每 token 打断读屏，具体效果需用目标读屏器验证。[依据：MDN log role](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/log_role)。

## 桌面分栏

拖动时保存起始尺寸；移动时将尺寸限制在两侧内容可用的范围内，释放后提交。推荐用 Pointer Events 与 pointer capture 保持同一文档内的拖动路由，并处理 `pointerup`、`pointercancel` 和捕获丢失后的收尾。跨 iframe 或嵌入式预览失去事件时，才按实测添加临时透明遮罩；遮罩、选区禁用和光标状态都须在结束或取消后清理。[机制依据：MDN pointer capture](https://developer.mozilla.org/en-US/docs/Web/API/Element/setPointerCapture)。

**本技能的可选交互约定：** 拖动期间 Esc 取消并恢复起始尺寸；双击恢复默认比例，同时提供可点击/键盘操作的恢复入口；需要自动收起时使用内容最小宽度及明确恢复入口。默认比例不必 50/50，收起阈值不固定 82%；取消与重置不丢编辑内容，也不永久占用整个应用的 Esc。

Web 可调分隔器应可聚焦、有名称、方向、当前值和范围，并支持与方向一致的方向键调节；可参考 APG 的 `separator` 方案。APG Window Splitter 当前仍带有未完成模式审查的说明，不把其示例参数当成已完成的通用实现。[依据：W3C APG Window Splitter](https://www.w3.org/WAI/ARIA/apg/patterns/windowsplitter/)。

除键盘外，为拖动提供单指针无需拖动的替代，如可点按的尺寸预设、增减或收起/恢复按钮；单独支持键盘不能满足拖动替代要求。窄视口下按项目响应式方案切换单栏或标签，不把两侧内容压到不可用。[依据：W3C WCAG 2.5.7](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements)。

## 文件名与识别信息

本技能建议在文件列表或附件卡片中保留有识别价值的扩展名或尾段，只裁剪显示，不修改真实名称、路径或下载元数据。CSS `text-overflow: ellipsis` 不会自动实现文件名中间省略；可把主名与已知后缀拆成可收缩/不可收缩两段，或使用目标框架已有控件。[机制依据：MDN text-overflow](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/text-overflow)。

完整名称仍可通过详情、可访问名称或可操作的展开/复制入口取得，不仅靠 hover；裁剪不能让两个文件无法区分。注意无扩展名、点文件、多段后缀及窄屏。显示的扩展名不能替代文件类型或安全校验。这些是文件展示建议，不是统一的文件命名标准。

## 验证与分工

只验证实际改动路径；已有自动化可覆盖状态转换，真实 IME 行为仍需目标系统和浏览器验证。没有运行界面时，不把文档检查报告成行为通过。

| 改动 | 有意义的验收场景 |
|---|---|
| 输入与发送 | 中文候选确认不发送；确认后正常 Enter 可发送；项目换行快捷键有效；按钮/默认提交无绕过；失败保留输入 |
| 滚动 | 底部跟随；上翻后 token/图片不抢位置；跳至最新恢复；前插历史不跳；程序滚动不误切状态 |
| 分栏 | 最小宽度、跨预览、拖动取消、捕获丢失、收起后恢复；方向键和无需拖动的点按替代 |
| 文件名 | 多段后缀、无后缀、长中文名；完整名称可获取且同名近似文件能区分 |

需要弹窗、确认或撤销时按导航读取 `ui-feedback-patterns`。边框、同心圆角、排版与动效属于 `ui-design-standards` 的视觉动效补充参考，避免在本技能重复存储视觉规则。
